## GedCode 0.5 replaces the Ged orchestrator

GedCode 0.5 is rebuilt on a new orchestrator. The old Ged orchestrator — the PM sessions and task stages from 0.4 — is deprecated and is not part of 0.5 in that form. Planning, implementation and verification now run through the new orchestrator: a lead thread hands work to planner, implementer and verifier agents, and the verifier is never the agent that did the work.

**What you keep:** your projects and threads. They open in 0.5 as regular threads.

**What you lose:** PM history — PM sessions, tasks, stage history and gates — does not carry over and is not shown in 0.5. It is not deleted: it stays in the 0.4 database (`~/.gedcode/userdata/state.sqlite`), and reinstalling GedCode 0.4.8 shows it again.

**Ged in any project.** Ged is no longer tied to the GedCode repository. To use it in a project, open its settings and choose **Set up Ged**, run _Set up Ged_ from the command palette, or ask an agent to set it up. GedCode shows the `.ged/` files it will add and never changes existing ones. Then start a thread at the project root: GedCode tells the agent the project uses Ged and serves it the process, so it is the same for every provider.

- **Models:** the lead picks each agent's model from its own family. Tell it which models you prefer and it records them in `.ged/model-notes.md`; if one is unavailable, it says so in the thread.
- **Verification:** a change lands only with a verdict from a verifier of another vendor than the agent that wrote it. Important changes can get two verifiers. With only one vendor installed, a same-vendor verdict is accepted with a warning.

Also new in 0.5:

- The command-line tool is `gedcode`, and project settings live in `gedcode.json`. An existing `t3.json` is no longer read; rename it to `gedcode.json`.
- New worktree branches are named `gedcode/…`.
- GedCode is now `com.gedcode.app` to macOS. If it asks again for permission to show notifications, that is why.
